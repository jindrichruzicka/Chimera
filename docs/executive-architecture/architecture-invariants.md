## Citing an Invariant

Docs and source files restate the rules they depend on. The number in each restatement is an index into this ledger; a wrong one sends a reader to a different rule with no signal that anything is off.

**The rule a citation must satisfy is this: it must share a term with the row it names.** A term is a case-folded run of letters and digits of four or more characters, drawn from code spans and prose alike — so `GameSnapshot` written in backticks and written plainly are the same anchor, while `the` and `any` are not anchors at all. Nothing stronger is required in either direction, deliberately: a citation is a short form, so it drops most of the row, and it may add a clause the row leaves implicit.

### The shapes that are checked

`#nn` is also how this repo writes an issue number, so each shape carries its own decision about what makes a `#nn` a citation at all:

| Shape                                                        | What makes it a citation                                           |
| ------------------------------------------------------------ | ------------------------------------------------------------------ |
| `- **Invariant #nn** — <short form>` opening a line in a doc | the `**Invariant #nn**` marker itself                              |
| A `#nn` row of a two-column table in a doc                   | the enclosing markdown heading names invariants                    |
| `Invariant #nn: <short form>` opening a source-comment line  | the spelled word, exactly as in the doc bullet — no block needed   |
| `#nn — <short form>` opening a source-comment line           | the line sits in a block opened by an `Invariants …:` heading line |

So a spec header that opens `#743 — E2E coverage for the in-game menu` is an issue reference, not a citation. Spelling the word is what turns a number into a claim about this ledger — which is why a claim the ledger does not make must not spell it.

### A claim the ledger does not make carries no number

An `Invariants …:` block admits entries with no number, and many are already written that way:

```ts
/**
 * Invariants upheld:
 *   #1 — simulation/ is side-effect-free; no Node.js or Electron imports.
 *   Module boundary — networking/provider/ has zero imports from renderer/ or electron/
 */
```

Outside a block the same convergence is simply not spelling the word. That is what to do with a property this ledger has no row for. A bare statement cannot cite the wrong rule; a number invented to look like a citation can only ever do that.

### What enforces it, and what it does not reach

`tools/invariant-citation-resolution.test.ts` owns every shape above — one rule, so one guard — over every tracked markdown file under `docs/` and every tracked `.ts`/`.tsx` file in the repo. It also reports a citation whose number names no row at all. The guard docblock is where its reach, its measured shared-term histograms, and its limits are stated; its fixtures are what enumerate the markers and separators that count.

Some things are deliberately outside it. A **mid-sentence reference** — "… (especially **Invariant #45** — `pruneTo` …)", "(Invariant #114)" — points at a rule rather than restating one, so there is nothing to resolve against. A **bare `#nn` opening a comment line outside a block** is left alone because nothing on the line says which ledger it indexes — this repo writes issue numbers in that exact shape, so reading the citations among them would mean reading the issue references too.

## Invariants 1–20

**1.** `simulation/` has zero runtime dependencies on React, DOM, or networking.

**2.** `applyAction`/`definition.reduce` are pure functions — same input, same output, always.

**3.** `GameSnapshot` never leaves the host's main process. `PlayerSnapshot` is the only state type that crosses any process or network boundary. Exception: the debug layer (`debug-bridge.ts`) returns full snapshots to the Inspector Window over `chimera:debug*` ("full truth — debug only", §4.12); it loads solely under the debug-mode gate (Invariant 27, whose exact expression §4.12 pins — it is deliberately not the imported `IS_DEBUG_MODE` constant) and validates every request sender against the Inspector's `webContents.id` (Invariant 29).

**4.** The renderer reads state; it never writes state directly.

**5.** All IPC methods are declared in `ipc-handlers.ts` and exposed only through `preload/api.ts`.

**6.** Network messages are validated before they touch the simulation.

**7.** `engine:undo` and `engine:redo` are `EngineAction` types — they go through the normal `ActionPipeline`. There is no side-door undo execution path.

**8.** `StateProjector.project()` is the mandatory gate between `GameSnapshot` and any outbound message. `StateBroadcaster` never reads `GameSnapshot` directly.

**9.** `CommitmentScheme.verify()` is always called client-side on receipt of a `REVEAL` message before the revealed value is trusted.

**10.** Game-defined action types and game definitions must be registered in `ActionRegistry` before the simulation tick loop starts. The engine never switches on raw `type` strings — all action delegation goes through `ActionRegistry.resolve()`, and game-level startup hooks go through `ActionRegistry.resolveGame()`.

**11.** The `engine:` action namespace is reserved. Games must not register action types starting with `engine:`.

**12.** `ActionPipeline` steps are invariant — parse before validate, validate before reduce. Games supply strategies; they do not control step ordering.

**13.** `ContentDatabase` is immutable after `ContentLoader.load()` returns, and the immutability is **deep**: `createContentDatabase` — the single freeze site every construction path funnels through — freezes each item **recursively**, so nested objects and arrays are frozen too, not just the item's own properties. A shallow `Object.freeze` does not satisfy this invariant; it holds only for content that happens to be flat today and silently lapses on the first nested field. The recursion domain is the JSON one Invariant #15 mandates — plain objects and arrays. A value JSON cannot produce, reachable only through the programmatic factory, is frozen but not descended into — the engine does not attempt deep immutability outside the content contract (an array-buffer view is skipped entirely, since `Object.freeze` throws on a non-empty typed array). It is never stored inside `GameSnapshot`. It is passed to `validate()` and `reduce()` through `PipelineContext`.

**14.** `ContentDatabase` is loaded and all schemas **and refs** validated before the tick loop starts. A failed load is a fatal startup error — the game does not start with incomplete content, and the engine **terminates** (`app.exit(1)`) rather than idling windowless, since the composition root launches `main()` as `void main(...)` where a bare throw is only an unhandled rejection. Ref integrity is checked **by default** in `ContentLoader.load()` (`ContentLoadOptions.validateRefs` defaults to `true`). Because content is untyped JSON, ref detection is structural, and its soundness rests on an **enforced** precondition rather than an assumption: every item id must match `ITEM_ID_SHAPE` (a non-empty run of non-whitespace — non-ASCII, dotted, slashed and colon-bearing ids are all legal), rejected as a `ContentSchemaError` by `createContentDatabase` — the same single factory that owns the Invariant #13 freeze, so the property holds for a directly-built database too. `ContentLoader` repeats the check at merge time for one reason: it runs before the duplicate check, so two id-less items are reported as malformed rather than as a `ContentConflictError` over a `Map` keyed on `undefined`. A string is then a ref exactly when its prefix names a known collection **and** its id half satisfies that same grammar — so a string the grammar rejects cannot name any item in the database, and skipping it can never skip a resolvable ref. What this guarantees, stated so it can be falsified: **every string reachable from a loaded item through object entries and array elements — keys as well as values, at any depth — whose prefix names a known collection and whose id half matches `ITEM_ID_SHAPE` must resolve, or the load fails.** Keys count because a map keyed by ref (`resistances: { 'damage-types:fire': 50 }`) is a first-class way to author per-ref data. Those two traversals are exactly what JSON can express, so over loaded content the sentence is total; a shape only a programmatic `inline` source can build — a symbol-keyed property, a non-index property on an array, a `Map`/`Set`'s contents — is not examined at all. What falls outside it is whatever that sentence does not cover, and is _not_ diagnosed at load, reaching `resolveRef()` at call time instead: an id half that is empty or contains whitespace (`units:`, `units:Fire Mage`), which by construction cannot name a legal item; a mistyped collection prefix (`unit:warrior` for `units:warrior`), which is not recognised as a ref at all; and a ref into a collection the loader never saw. The converse cost is inherent to detecting refs in untyped JSON and is accepted deliberately: a string that merely _looks_ like a ref — an i18n key `units:warrior_name`, a `data:`-style value — becomes a **fatal** load error in a game that has a `units` collection, because nothing distinguishes it from one. A game hits this only by naming a collection after another of its namespaces. `validateRefs: false` is the escape hatch, and otherwise a narrow opt-out for a deliberately partial load whose refs resolve against a database that call does not build; no production startup path may use it.

**15.** Game-defined content must never contain executable code. The engine loads JSON only; content files are pure data.

**16.** AI players submit `EngineAction` through `ActionPipeline` — there is no back-door mutation path for AI.

**17.** AI receives a `PlayerSnapshot` **produced by `StateProjector.project()`** by default (honest AI), on **every** state-delivery path — the seed handed to `AIStateMachine.setInitialState` at agent construction as much as the per-tick `AgentManager` fan-out (`tickAll` / `onGameStart` / `onGameEnd`). Structurally widening a `GameSnapshot` into `PlayerSnapshot` shape by spread is not a projection: it type-checks (TypeScript does not excess-property-check spread-in members) while carrying `seed`, `turnClock`, `turnNumber`, `hostPlayerId`, `timers`, `committedTurns`, and every game-local root field. Omniscient mode (`GameSnapshot` access) must be declared explicitly in the game's AI configuration and is logged at game start; the sanctioned omniscient spread lives solely in `AgentManager` and in `buildDefaultAIPlayerAgent`'s seed branch.

**18.** `AIParams` are passed by value (frozen) to every lifecycle method — AI state and command implementations must not mutate them.

**19.** At most one state transition is applied per AI tick. If multiple transitions are requested within a single tick, the last one wins; earlier requests are discarded and a warning is logged.

**20.** `simulation/` never resolves `AssetRef` values. `AssetRef` strings stored in `ContentDatabase` data objects are opaque to the simulation. Only `renderer/assets/AssetManager` may resolve them to loaded GPU or audio resources.

## Invariants 21–40

**21.** `AssetManager.dispose()` is called unconditionally on every game session end. Components must never hold direct references to loaded Three.js assets — all access goes through `useAsset()` or `AssetManager.get()`. The single exception is the per-instance model clone obtained from `useModelInstance()`: the clone is component-owned and never outlives its component, and it must never dispose, mutate, or re-bind any resource it shares with the cached asset — geometries, materials, textures, `geometry.morphAttributes`, animation clips, or `skeleton.boneInverses`. `AssetManagerProvider` only publishes, never constructs or disposes: the engine app root mounts the one live provider (publishing the app-level delegating manager the app root also disposes), `GameShell` is the unique disposer of the **match-level** manager, and a game-mounted provider publishes a double whose lifetime the game owns. One further owner exists for surfaces with no `GameShell` above them: `GameAssetSession` (`renderer/app/gameAssetSession.tsx`, reachable by an app's own Next host tree as `@chimera-engine/renderer/shell/gameAssetSession`) builds, publishes **and** disposes a game-asset manager for a route that renders a game's assets outside a match — on unmount and on every manifest-identity change, because nothing else will. It is not a competing owner of the match-level manager: it registers no `SetGameAssetManagerContext` delegate, so the app-level `AudioManager` still reaches only a real match's assets. Its manager is allocated in a commit-phase effect, never in render — a `useMemo`/`useState` allocation orphans one manager under StrictMode, which discards one render-phase result and runs no cleanup for the discarded render. The two routes that hand a manager to `GameShell` (`/game`, `/replays/player`) build theirs through the same module's `useRendererGameAssetManager`, which memoises but deliberately never disposes, leaving that to `GameShell`.

**22.** All `AssetRef` strings in content JSON files must pass `electron/dev-tools/validate-assets/index.ts` before merge. A data object referencing a non-existent file is a CI-blocking error, not a warning.

**23.** `FileSaveRepository.save()` always writes to a `.tmp` file and renames atomically. A save must never partially overwrite a previous valid save file.

**24.** `SessionRuntime.applyRestoredFile()` is the only entry point for replacing the live `GameSnapshot` from a file. The two-step load flow is: (1) `SaveManager.restoreFromSave()` reads and migrates the file from disk into a `SaveFile`, then (2) `SessionRuntime.applyRestoredFile(file)` replaces the live snapshot. Its two callers are the in-session load branch (same-match live apply) and the `SessionRestoreCoordinator` menu-restore flow (F68 #823) — both funnel through the composition root's single apply helper; the coordinator is a caller, not a bypass. No other code path may overwrite the running simulation state from disk. Swapping the snapshot must leave the **whole hosted session** consistent with the restored file, not just the snapshot: per-agent AI state (state machine, command scheduler, latches) is host-local and outside the deterministic snapshot (host-local state ownership, Invariant #3), so both callers rebuild the agent roster against the restored checkpoint — the menu flow seats fresh agents (`seatRestoredRoster`), and the in-session branch clears + re-seats them (`rebuildAgentsAgainstRestoredSnapshot`, #907), each re-seeded through its projected construction seed (Invariant #17) — so no agent's host-local state outlives a rewind.

**25.** `engine:save` and `engine:load` are validated `EngineAction` types — only the designated host player may dispatch them. Client-originated save/load actions are rejected by `validate()` before reaching the reducer.

**26.** `SaveFile.pendingCommitments` must be restored into `CommitmentScheme` on load. A loaded game without restored commitments must not process any `REVEAL` messages until commitments are present.

**27.** `CHIMERA_DEBUG` must never appear in the production packaging configuration. A **production runtime** is any process that is either packaged (`app.isPackaged`) **or** launched with `NODE_ENV=production` — electron-builder never sets `NODE_ENV`, so packaging alone must trigger the guard. Every production runtime must assert `IS_DEBUG_MODE === false` at startup and refuse to start if `process.env.CHIMERA_DEBUG` is set (`electron/main/startup-guard.ts` — `isProductionRuntime` / `assertProductionDebugGuard`, called with `app.isPackaged` from the `main()` composition root).

**28.** `window.__chimeraDebug` is exposed only by `debug-api.ts` and only to the Inspector Window. The game renderer's `api.ts` preload must never expose any debug **data** surface — no snapshots, projections, diffs, action logs, or perf stats. The data-free Inspector-window toggle (`system.toggleDebugInspector()`, a payload-less send on `chimera:debug:toggle-inspector`) is explicitly permitted; outside debug mode no listener is registered and the send is a no-op.

**29.** The debug `ipcMain` handler (`chimera:debug`) must validate `event.sender.id` against the Inspector Window's `webContents.id` on every request. Any request from a different sender returns `{ type: 'ERROR' }` immediately.

**30.** `SnapshotRingBuffer` has a fixed capacity. It must never grow unboundedly. Oldest entries are overwritten silently; the capacity is configurable but must be explicitly set — no dynamic growth.

**31.** `SnapshotInspector` and `SnapshotRingBuffer` are instantiated only when `IS_DEBUG_MODE` is true. The `debugObserver` field in `PipelineContext` is undefined in production; the optional-chain call `context.debugObserver?.()` is the only simulation-side debug coupling.

**32.** Settings are never stored inside `GameSnapshot`, `SaveFile`, or `PlayerSnapshot`. Settings have a completely separate lifecycle from gameplay state and are not replayed, diffed, or included in undo history.

**33.** `FileSettingsRepository.save()` always writes to a `.tmp` file and renames atomically. A settings write must never partially overwrite a previous valid settings file.

**34.** `SettingsManager.registerSchema()` must be called for a game before `getSettings()` or `updateSettings()` is called for that game. Calling `getSettings` for an unregistered `gameId` returns only engine defaults and logs a warning — it does not throw, ensuring graceful degradation.

**35.** The four top-level engine namespaces (`audio`, `display`, `gameplay`, `controls`) must reach `SettingsManager.registerSchema()` **intact**: each present in the game's `defaults`, an object, and owning every engine sub-key for that namespace. A game must not shadow a reserved namespace with its own value, supply a partial one, or omit one — all three degrade `SettingsMerger.mergeAll()` identically, since it walks the base tree and would drop both the namespace and the user's stored overrides for it. A bare key-name check cannot express this: `GameSettingsSchema<T extends EngineSettings>` means every game's `defaults` legitimately _contains_ all four keys (games spread `...ENGINE_DEFAULTS`). `registerSchema()` enforces intactness at startup, throws `SettingsNamespaceCollisionError`, and the engine composition root refuses to start on it. The check is structural — sub-key ownership only, never sub-value types or ranges; game `defaults` are trusted first-party input and are range-validated on no runtime path. `GameSettingsPageDefinition` `game-field.path` entries must be backed by the registered game settings schema; presentation metadata never admits unregistered settings keys.

**36.** Settings are never read by the simulation core (`simulation/`) or the `ActionPipeline`. Any game parameter that must affect simulation outcomes must be declared as a match config value and transmitted as part of lobby setup, not as a user setting.

**37.** `SaveManager` must be constructed with an injected `SaveRepository` instance. No code inside `save-manager.ts` imports `FileSaveRepository` or any other concrete class by name. The concrete implementation is chosen once in `electron/main/index.ts`.

**38.** `LobbyManager` must be constructed with an injected `MultiplayerProvider` instance. No code inside `lobby-manager.ts`, `ipc-handlers.ts`, `StateBroadcaster.ts`, or `MessageRouter.ts` imports `LocalWebSocketProvider` or any other concrete provider by name.

**39.** `StateBroadcaster` and `MessageRouter` must not import from `networking/server/` or `networking/client/`. They interact exclusively through `HostTransport` and `ClientTransport` interfaces. Provider-internal directories are off-limits to all other modules.

**40.** A `MultiplayerProvider` instance must not be disposed or replaced while a `HostedSession` or `JoinedSession` is active. `LobbyManager.closeLobby()` must complete before `provider.dispose()` is called. Provider swaps are a cold-boot concern only — no hot-swapping during a session.

## Invariants 41–60

**41.** `InMemorySaveRepository` must pass the identical contract test suite as `FileSaveRepository`. Any divergence between their observable behaviors for the same inputs is a bug in the in-memory implementation, not an acceptable simplification.

**42.** The simulation is action-driven. `GameSnapshot.tick` is incremented by exactly 1 per action applied by `ActionPipeline.process()`. It is never derived from `Date.now()`, `performance.now()`, or any wall-clock source.

**43.** `validate()` and `reduce()` must be pure given `(state, payload, playerId, ctx)`. They must not call `Math.random`, `Date.now`, `performance.now`, read environment variables, or access any I/O. The only permitted source of randomness is `ctx.rng`.

**44.** All numeric fields of `GameSnapshot` that participate in arithmetic, comparison, or checksums must be integers (including fixed-point representations of money, percentages, and fine-grained positions). Floating-point is forbidden in simulation state.

**45.** `ActionHistory` is bounded by `TurnMemento`. Retention is `TURN_MEMENTO_RETENTION = 4` turns (entries with `turnNumber < currentTurn - TURN_MEMENTO_RETENTION` are evicted by `pruneTo`). `pruneTo(cutoff: number)` is idempotent: calling it repeatedly with an identical or lower cutoff is a no-op; the comparison is strict `<`, never `<=`. A `MAX_ACTION_HISTORY_ENTRIES = 10_000` safety-net cap guards against pruning bugs: on overflow, `append()` evicts oldest entries AND emits an `action-history:overflow` warn log.

**46.** `ContentDatabase` is optional. Games that declare no content (e.g. Tic Tac Toe) pass no `db` to `PipelineContext`, and `ReduceContext.db` is `undefined` for them. `validate()` and `reduce()` must tolerate `ctx.db` being `undefined` if the game opts out.

**47.** `StateBroadcaster`, `MessageRouter`, `LobbyManager`, `SaveManager` and all other main-process orchestration modules must not import from `networking/provider/local/` or any other provider-specific subdirectory. Cross-module communication goes exclusively through `MultiplayerProvider`, `HostTransport`, and `ClientTransport`.

**48.** Game UI beyond the engine's built-in shell lives in `apps/<name>/screens/` and is registered via `GameScreenRegistry`. `GameShell.tsx` is game-agnostic — it never imports from any specific game package.

**49.** Scene transitions are host-authoritative. `engine:scene_prepare` and `engine:scene_commit` are rejected if the dispatcher is not the host player. (See [Scene Transitions](../core-components/scene-transitions-fade.md).)

**50.** `SceneDescriptor.initialize()` and `teardown()` are pure reducers. They may not perform I/O, call `Date.now()`, or read from `Math.random()`. They receive `ReduceContext` and use `ctx.rng` for any randomness.

**51.** Clients never drive a scene change. A client that wishes to transition sends a domain action; host-side policy decides whether to honour it via `SceneManager.requestTransition()`.

**52.** Required assets for a scene MUST be declared in its `SceneDescriptor.requiredAssets`. Assets loaded on-demand inside the new scene will cause visual pop-in. `validate-assets` verifies that every **declared** `AssetRef` — in `requiredAssets`, asset manifests, content JSON, and font `src` — resolves on disk, and that `requiredAssets` and content-JSON refs additionally appear in an asset manifest (Invariant #22). A manifest entry's `ref` counts as declared when it is statically readable: a string literal, a `buildAssetRef(...)` call, or a `<Const>.<member>` naming a const **declared in that same manifest file** (the shape the `audioClipEntry` builder invites, since the const already exists for the game's own screens to name the clip). A ref the walker cannot read contributes nothing at all rather than failing — so an entry whose `ref` is computed, imported, or reached through a nested access silently leaves both this check and the membership set below, exactly as an unwrappable entry element does (#125). The const scan is textual and scope-blind: it walks the whole file, function bodies included, and keeps whichever declaration of a name comes **last in source order** — not whichever is in scope at the entry. That is the same collector the on-demand scanner's tier B has always used. It also statically **scans** **on-demand load** call sites (the ref-taking loader hooks enumerated by `ON_DEMAND_LOAD_HOOK_NAMES` in `electron/dev-tools/validate-assets/index.ts`, plus `assetManager.load(...)`/`.get(...)` on an asset-manager receiver; a ref that reaches the engine only as a JSX PROP — `<AnimatedSprite sheet={ref}>` — is a known blind spot, since the scan matches call expressions) across scene/screen-segment paths and the `apps/<name>/components/`, `apps/<name>/shell/` and `apps/<name>/renderer/` game surfaces Invariant #96 legalises, and flags an **undeclared on-demand load** whose ref is statically resolvable — a string literal, `buildAssetRef(...)`, or a manifest-const member — as a CI-blocking error. Refs it cannot statically resolve (dynamic or computed) are **warned**, never failed; membership is checked against the workspace-wide union of declared refs, **not per-scene** (the imperative `SceneRegistry` map exposes no file↔descriptor association). The `.load`/`.get` scan recognises only asset-manager-named receivers, so a load through an aliased or destructured receiver is a known blind spot; manifest-const members resolve against the caller's own game only. The declaration now has its first RUNTIME consumers, which is a change in what `requiredAssets` does rather than in where it is declared: a scene being entered carries the list on `SceneTransitionState.requiredAssets`, where `startScenePreload` promotes and awaits it before the client acknowledges the transition, and a scene already committed carries it on `BaseGameSnapshot.sceneRequiredAssets`, where `useCriticalAssetPreloadGate` promotes it for the route-entry run. Both are bounded and fail-open (Invariant #133); the declaration site and every check above are unchanged, and a runtime FETCH failure remains something `validate-assets` cannot see.

**53.** `TransitionOverlay` is a renderer-only component. The simulation and Electron main process have no knowledge of fade state. Fade timing must never gate an authoritative simulation event — the `SceneReadyAction` is dispatched _after_ the fade completes, not as a cause of it.

**54.** `GameTimer` lives in `GameSnapshot.timers`. It is serialised, loaded, and replayed. A timer's `remainingTicks` counter must never be derived from wall-clock time.

**55.** `TimerManager.advance()` is a pure function. The `engine:tick` reducer is the ONLY consumer of `TimerManager.advance()`. Game action reducers may create or cancel timers but must NOT call `TimerManager.advance()`.

**56.** `curves.ts`, `useTween`, and `useTweenCallback` are renderer-only modules. They must never be imported by anything under `simulation/`. Visual smoothing is a client-local concern; the authoritative state does not move smoothly.

**57.** Camera state is renderer-only. `GameSnapshot` must never contain camera position, look-at, zoom, or any other camera parameter. Camera configuration is driven by game playfield components in response to snapshot data — it is never driven by authoritative simulation actions.

**58.** `isHovered` in `useGameInteraction` is local component state. It must never be written to any Zustand store, IPC message, or simulation state. Hover is a transient renderer-local concern.

**59.** Player profile data (avatar, display name, locale, game-defined profile fields) is never stored in `GameSnapshot`, `PlayerSnapshot`, or `SaveFile`. It is a lobby-scoped cosmetic concern, separate from gameplay state, and is not replayed, diffed, or included in undo history.

**60.** `ProfileRepository` persists only the _local_ machine's profiles. The host's repository never receives or persists remote clients' profiles — remote profiles live only in the in-memory `PlayerDirectory` for the lifetime of the session and are discarded on lobby close.

## Invariants 61–80

**61.** `ProfileSanitizer.admit()` is the mandatory gate between an inbound `JOIN` / `PROFILE_UPDATE` attestation and the `PlayerDirectory`. Size caps, MIME whitelist, image decode check, display-name length, and game-schema validation all run inside `admit()`. A failed admission results in a `REJECT` response — the raw attestation is never exposed to any other subsystem.

**62.** Profile changes travel out-of-band from the `ActionPipeline`. `PROFILE_UPDATE` is not an `EngineAction`, does not advance `tick`, and does not participate in undo/redo or save/load. Any renderer component reading profile data must read it from the profile directory — never from `PlayerSnapshot`.

**63.** The simulation never produces audio. Audio playback is initiated only by the renderer in response to `GameEvent`s or direct UI interactions. No reducer, validator, or `ActionDefinition` may import from `renderer/audio/`.

**64.** `AudioManager.dispose()` is called unconditionally at engine shutdown (app exit). `Providers` (`renderer/app/providers.tsx`) is the unique owner of `dispose()` for the app-level `AudioManager`. Since the public `@chimera-engine/renderer/audio` barrel (Invariant #96) hands a game surface the same manager instance through `useAudioManager()`, that ownership is now a rule game code is subject to and not merely an engine-internal arrangement: a game may start and act on its own voices, but must never call `dispose()` — it would invalidate every other component's handles — and `stopAll()` is the engine's session-end call, not a game's. Nothing mechanical holds this; the narrower `useMusicTrack()` control object exists so that a component holding music controls need not take the manager at all. At game session end (match phase `ended`), `GameShell` calls `AudioManager.stopAll()` to stop all active voices — it does **not** call `dispose()`. Active `AudioHandle`s become invalid after `dispose()`.

**65.** `InputManager` is renderer-only. The simulation has no knowledge of keyboard or gamepad state. Input translates into `EngineAction`s via `sendAction()` at the renderer boundary — never directly into reducers.

**66.** Key bindings are settings, not profile data. They follow the settings layered-merge contract (engine defaults ← game defaults ← user overrides) and are stored under `settings.controls.bindings`. They are not transmitted over the network and never appear in `GameSnapshot`.

**67.** Every main-process manager is constructed with an injected `Logger` child. No module emits logs via raw `console.*` — all structured logging flows through the injected logger. Two sanctioned exceptions, each of which must cite this invariant in an in-code comment: (a) the Invariant #27/#77 startup guard in `main()`, which runs before the root logger is constructed and must be the first statement so no debug surface initialises before an illegal combination is caught — it writes the refusal reason to `stderr` via `console.error` before `app.exit(1)`; (b) the preload layer (`electron/preload/shared/listener.ts`), which has no injected logger and reports validation drift to the renderer devtools console. Exception (a) is enforced as a ratchet rather than a convention: a `no-console` ESLint zone covers `electron/main/**` and each consumer composition root (`apps/*/electron/main.ts`) with no `ignores` — test files included — and that guard is the single `eslint-disable-next-line` in the tree, so a second raw `console.*` call cannot land without an explicit, reviewable disable. The zone is itself pinned by `electron/main/__tests__/eslint-no-console.test.ts`, because deleting it from `eslint.config.mjs` leaves `pnpm lint` green — the only trace is an unused-disable _warning_, and no package sets `--max-warnings`. That test checks three independent things, since each is defeatable alone: that the rule discriminates (fixtures), that the zone declares it once at `error` with no `ignores`, and that ESLint _resolves_ it at error severity for a file from every subtree — the config's global `ignores` can exempt a subtree without the zone changing at all. Every refusal raised **after** the logger exists takes no exception and shares one shape, because there is one implementation of it rather than a convention each site re-applies: they all call the single `refuseToStart(logger, sink, message, err)` helper in `main()` — currently the Invariant #14 content load, the Invariant #35 settings registration, and the dev-harness bootstrap failure — which reports through the injected `logger` at `fatal` (the level is what makes a refusal findable in the log file a packaged binary leaves behind), drains the sink with `flushSync()`, then calls `app.exit(1)`. The sink write is buffered (`minLength: 4096`) and `app.exit()` emits no `before-quit`, so the flush is what makes the report real; both steps are guarded so that neither can skip the exit and reinstate the live, windowless process the refusal exists to prevent. Relatedly, a logging call must never throw into its call site: `createFanOutSink` isolates each sink from the others (one failing transport must not deny the rest the entry, and the Pino sink is written first), and the console sinks additionally swallow an unwritable or unrenderable line. Isolation is not silence — a failing leg is announced by name on the legs that still work, because no sink reports its own failures and the Pino sink is the only durable one. Once per _run_ of failures, not per entry and not per session: the file sink fails both permanently (a dead fd, which recurs on every entry) and transiently (an entry it cannot serialise), so the latch clears as soon as that leg writes again. The same rule applies to both paths that end a process: `refuseToStart` and `handleUncaughtException` each guard their report and their drain, so neither a throwing sink nor an unflushable one can skip the exit and leave the live, windowless process it exists to prevent. A `LoggerSink` writing to stdout or stderr is transport, not a `console.*` call site, and takes no exception either: the dev-harness stdout sink (§4.32) and the dev terminal mirror (`createStderrSink`, wired at `error` and above for an unpackaged, non-harness launch) put those refusal reasons back on the terminal without any module bypassing its injected logger. The **renderer** takes no exception either, but nothing there is injected and no `no-console` zone applies: `installRendererLogger` (`renderer/logging/rendererLogger.ts`) _patches_ `console.warn` and `console.error` and forwards each call over `window.__chimera.logs`, so in `renderer/**` those two methods **are** the bridge and the main-process rule does not transfer — the failure mode is not a raw `console.*` call site but a call the bridge never saw or could not carry, which the invariant's intent forbids just as squarely. Two properties therefore hold it up, each pinned by test rather than by convention, because neither is visible from a call site. First, the bridge is installed before the first **render-phase** log, not merely before the siblings of whatever mounts it: `<LoggingBootstrap />` is `AppShell`'s first child, outside `<Providers>`, and installs **during its render** rather than in a `useEffect`, since React runs a parent's render strictly before any child's effect — `renderer/app/AppShell.test.tsx` pins it by making `Providers`' render-phase AudioManager warn reach a `logsApi` stub (that warn previously reached devtools and never the log file), and `renderer/app/LoggingBootstrap.test.tsx` pins the install's idempotency, its re-arm across StrictMode's simulated remount, its refusal to claim a bridge another owner installed, and its exact teardown (console methods restored and window listeners removed). The guarantee is bounded at React: client-bundle **module evaluation** — including the `chimera-game-registration` side-effect import that runs an adopter's `register.ts` as the bundle loads — precedes every render and sits outside the bridge, so module-scope code must not log expecting forwarding. Second, an `Error` handed to the patched `console.warn`/`console.error` reaches `LogEntry.error` as `{ name, message, stack }` — the stack is the whole reason a renderer error is actionable — and is removed from the composed `message` so its detail travels once; the remaining arguments compose `message` unchanged, and fields are truncated renderer-side to the `chimera:logs:emit` schema caps so an oversized stack costs characters, never the entry (the handler drops what fails validation). One asymmetry with the main process is deliberate and must stay stated: a renderer forward that throws is swallowed by the bridge's re-entry guard and announced **nowhere** — the renderer has no counterpart to the fan-out's failed-leg announcement, and the entry survives only in devtools. `console.log` is deliberately **not** forwarded (§4.27, PII/volume hygiene); a call site needing a durable record moves up to `warn`/`error`, and `renderer/logging/rendererLogger.test.ts` pins the non-forwarding so a later completeness change cannot quietly reverse it.

**68.** The crash reporter runs autosave before writing the crash dump when a live simulation is present. The crash dump file is created atomically (`.tmp` + rename) so a partially-written crash dump never exists.

**69.** No log entry, crash dump, or telemetry ever leaves the user's machine automatically. Export is an explicit, user-initiated action. The main process must not register network telemetry in 1.0.0.

**70.** `ReplayPlayer` uses the same `ActionPipeline` instance wiring as live play. Any "replay-only" shortcut code path is forbidden — a replay divergence is a determinism bug, not an acceptable replay-layer simplification. This invariant governs **deterministic replay playback only**; a _perspective_ replay (Invariant #98) is never re-simulated — playback walks its stored `PlayerSnapshot` frames in order and never touches `ActionPipeline` — so this rule does not apply to it.

**71.** Deterministic replay files (`ReplayFile`, no `kind` discriminator) contain full `EngineAction` payloads — never projected `PlayerSnapshot`s. Playback starts from seed + gameConfig and reconstructs state through the pipeline. A replay file without `seed` or `actions` is malformed and rejected at load. (The distinct _perspective_ replay format of Invariant #98 deliberately inverts this — it stores projected snapshots and no seed/actions — and is identified by its `kind: 'perspective'` discriminator.)

**72.** `CHAT` messages are not `EngineAction`s. They must not advance `tick`, invoke `ActionPipeline`, or be recorded in `ActionHistory` / replays / saves. Chat is a cosmetic communication channel, parallel to `PROFILE_UPDATE`.

**73.** `ChatRelay.relay()` is the mandatory gate between an inbound `CHAT` message and rebroadcast. Length cap, rate limit, and scope validation all run inside `relay()` — no bypass path exists.

**74.** `toastStore` is renderer-only state. Toast contents must never be derived from `GameSnapshot`, `PlayerSnapshot`, or `SaveFile`. Toasts are transient UI surfaces for the local viewer; other players do not see another player's toasts.

**75.** `FixedPoint` is the ONLY allowed fractional representation in `GameSnapshot` and `EngineAction.payload`. A game that stores `number` for a fractional gameplay quantity violates invariant 44 even if it rounds consistently — determinism requires the shared `bigint` Q32.32 representation.

**76.** `fromFloat()` is permitted only at content-load time for hard-coded constants. It must not be called inside `validate()`, `reduce()`, or any hot simulation path. Linting is enforced by a dedicated ESLint rule in CI.

**77.** The dev multiplayer harness is a development-only tool. `electron/main/index.ts` must refuse to start when `CHIMERA_DEV_HARNESS=1` is combined with a **production runtime** — packaged **or** `NODE_ENV=production`, the same `isProductionRuntime` predicate as Invariant #27 — and every harness flag must be ignored (with a warning) when `CHIMERA_DEV_HARNESS` is absent.

**78.** Each harness-spawned instance runs in an isolated Electron `userData` directory (`.dev-userdata/p<i>/`). Shared state between instances is forbidden — profiles, saves, settings, logs, and crash dumps must be per-instance so the harness behaves identically to multiple distinct machines. The host's announce file (the lobby-code handshake) lives inside the host's OWN `userData` dir and is read only by the orchestrator CLI — an instance never reads another instance's directory.

**79.** All `registerExtension()` calls must complete before `api.ts` is loaded. `buildExtensionsApi()` is called exactly once, immediately before `contextBridge.exposeInMainWorld`. A late registration after `buildExtensionsApi()` has run will mutate the internal registry but the frozen copy already handed to `exposeInMainWorld` will not reflect it.

**80.** `GameShell.tsx` and `InGameMenuHost.tsx` must never import from any `apps/*` path. The `GameScreenRegistry` passed as a prop is the sole coupling point between the engine renderer and a game's React code; the `inGameMenu` slot reaches `InGameMenuHost` only through that registry (F55).

## Invariants 81–90

**81.** `GameScreenRegistry.playfield` is the only required slot. All other slots are optional. A game that provides only `playfield` is a fully valid Chimera game.

**82.** Within-scene panel navigation (`useNavigateToScreen`) is a renderer-local state change. It must never trigger an IPC call, advance `tick`, or dispatch an `EngineAction`.

**83.** All engine-provided React contexts use `createContext<T | null>(null)`. The consumer hook must throw a descriptive error if the context is `null`. `createContext<T>(null!)` (the "null-bang" pattern) is forbidden in engine code. Sanctioned carve-out: `IconContext` (the game-contributed icon set, Invariant #113) still uses the `null` default but exposes **no throwing consumer hook** — `<Icon>` reads it inline and **degrades** to the engine `ICON_REGISTRY` when `null`, because rendering `<Icon>` with no `IconProvider` mounted is a first-class supported case (the component gallery, unit tests, the engine-only shell).

**84.** Game screen components must not import `AssetManager`, `ContentDatabase`, or `AudioManager` as singleton module-level imports. All access goes through the context hooks (`useAssetManager()`, `useContentDatabase()`, `useAudioManager()`).

**85.** Game token override files may only redefine tokens declared in `renderer/styles/tokens.css`. Introducing new `--ch-*` custom property names in a game's override file is a module-boundary violation.

**86.** Engine UI components (`renderer/components/ui/`) must not contain hardcoded colour, spacing, or radius values. Every visual attribute must reference a `var(--ch-*)` token or a scoped CSS Module class — never an inline hex value. Icon glyphs (engine `ICON_REGISTRY` entries and game-contributed `GameIconSet` entries, Invariant #113) extend this at the SVG level: a glyph's `content` carries **no `fill`**, so it inherits `fill: currentColor` and `--ch-size-icon` sizing from the shared `.icon` rule and tracks its host control's colour token — a game glyph therefore renders identically to a built-in, including inside an `<IconButton>`.

**87.** Every screen component exported from `apps/<name>/screens/index.ts` must be wrapped in `React.lazy()`. Eager static imports of large screen components into the registry module are forbidden — they defeat the bundle split and load all game UI on match entry.

**88.** `GameShell` wraps every active screen in a `<React.Suspense>` boundary. No game screen component may assume it renders without a Suspense ancestor. `SceneRouter` renders a further boundary around the ACTIVE screen, and that one's fallback is registry-resolved rather than fixed: `resolveLoadingScreen` reads `GameScreenRegistry.loadingScreens[screenKey]` first, then the registry-wide `loadingScreen`, and resolves to the engine's own empty placeholder when neither is declared — visually nothing, and unchanged from before the slots existed — while `'none'` opts one key out of a registry-wide cover. The same cascade renders at the scene-transition and route-entry cover sites, which are SIBLING layers rather than Suspense fallbacks (§4.36, Invariant #133). The minimum-visible hold's held layer may re-render the Suspense site's SAME cascade resolution as a sibling for the hold's remainder after the fallback drops; the cascade and its resolution order are unchanged. That held layer now stands in for a VISIBLE fallback's early unmount alone — a declared hop's chunk folds into `useLoadingBeat`'s wait and its suppressed fallback never arms the hold, there being no visibility for a minimum-visible floor to protect. While that hop cover is mounted the Suspense fallback renders its REPORTER but no cover: the hop layer paints scrim above it, so a second resolution would be invisible and would still announce the same wait twice through `role="status"`. The cascade a fallback resolves when it does render, and the order it resolves it in, are unchanged.

**89.** `ctx.dispatch()` nesting depth is bounded by `MAX_NESTED_DISPATCH = 16`. `ActionPipeline` throws `RecursiveDispatchError` when this ceiling is exceeded. Only `engine:tick` may call `ctx.dispatch()`. This bound is reflected in `ReduceContext.dispatchDepth` and is invariant-backed per the JSDoc contract on `ReduceContext` in `simulation/engine/types.ts`: adding fields to `ReduceContext` requires a dedicated invariant in this document.

**90.** `ReduceContext.logger?: Logger` is engine-internal diagnostics surface, populated by `ActionPipeline` from its injected `Logger` instance. It is intentionally absent from the public `GameReduceContext` interface (ISP) and is reachable only after a deliberate `isReduceContext()` narrowing call. Use is restricted to engine-reserved actions: today only `engine:tick` (which emits `warn`-level entries when a timer-fired action is rejected by `validate()` — non-fatal, see §4.20). Game reducers must never read or write this field; any future engine-reserved action that uses it must update this invariant.

## Invariants 91–134

**91.** Shell page components (`main-menu`, `lobby`, `settings`, `saves`, `component-gallery`) must not set hardcoded colour, spacing, or radius values in any inline `style` prop. Every visual attribute must reference a `var(--ch-*)` custom property (§4.35, §4.37).

**92.** Shell pages must use `<Button>` from `renderer/components/ui/` for all interactive actions. Raw `<button>` or `<input type="button">` elements with inline styles are prohibited in shell pages. (See [Renderer Shell Pages UI Contract](../core-components/renderer-shell-pages-ui-contract.md).)

**93.** Game token override CSS must not be imported directly by any shell page component. Token overrides enter the cascade exclusively as side-effects of game registry initialisation — importing `apps/<name>/styles/tokens-override.css` from a shell page file is a module-boundary violation.

**94.** Engine shell pages (`main-menu`, `settings`, `saves`, `component-gallery`) must not import from any `apps/*` path. The lobby page may import `LobbyConfig` parsing helpers but must not import game-specific screen modules, registries, or override stylesheets directly.

**95.** `chimera:game:get-current-snapshot` is a read-only renderer-to-main IPC replay channel. It may return only the most recent projected `PlayerSnapshot` already stored for renderer delivery, or `null` when no snapshot has been sent. It must never expose `GameSnapshot`, accept renderer payload that changes gameplay state, trigger `ActionPipeline`, or mutate simulation state.

**96.** Game renderer surfaces may import the shared renderer library only through its **eight** public barrels — `@chimera-engine/renderer/components/ui` (stateless design primitives, §4.35), `@chimera-engine/renderer/components/chat` (the shared chat component, §4.35.1), `@chimera-engine/renderer/components/r3f` (the curated engine R3F surface: the `GameCanvas` root — the only canvas root a game mounts, Invariant #127 — plus the Canvas-bound `useModelAnimation`, `useClipPlayer` and `useSpriteClipPlayer` hooks, the `AnimatedSprite` element that packages the sprite half, the `useAnimationTimeScale` dilation seam, the tween and camera surface `useTween` / `useTweenCallback` / `useCamera` with the `CameraAnimationCancelled` error and the `lerp` / `linear` / `easeIn` / `easeOut` / `easeInOut` curve primitives a caller passes to them, the pointer-interaction pair `useGameInteraction` / `useInteractionContext` and the `InteractionBlocker` provider `GameCanvas` already mounts — the raw `InteractionContext` stays internal, so a game nests a provider rather than building one — and the curated types, §4.16, §4.21, §4.22, §4.23), `@chimera-engine/renderer/game` (the game-registration seam a renderer composition root calls), `@chimera-engine/renderer/i18n` (the i18n runtime, §4.39), `@chimera-engine/renderer/audio` (the audio hooks `useSound` / `useMusicTrack` / `useAudioManager` and the cue/fade option types they take, §4.25), `@chimera-engine/renderer/assets` (the asset hooks `useAsset` / `useAssetManager` / `useModelInstance` / `useAnimationSheet` / `useSpriteAnimationSheet` / `useSpriteAtlas`, the `parseSpriteAtlas` reader under the last of them, the `AssetManagerProvider`, and the asset, error, atlas and parsed-sheet types they take, §4.10), and `@chimera-engine/renderer/input` (the subscription hooks `useInputAction` / `useInputManager`, the `InputManagerProvider`, and the `InputAction` / `InputActionId` / `InputEvent` / `InputManager` types they take — the manager factory, the action registry and the key-binding repository stay internal, so a game consumes the app-lifetime manager and never builds one, §4.26). This allowance is limited to game screen components under `apps/<name>/screens/*.tsx`, the game's reusable React under `apps/<name>/components/*.tsx`, React shell contributions under `apps/<name>/shell/*.tsx`, and the renderer composition root `apps/<name>/renderer/*.{ts,tsx}`. `components/` is one surface, not two: it holds every reusable piece of a game's UI — DOM components, the in-Canvas `three` / `@react-three/fiber` primitives a screen renders as children of its `GameCanvas`, and the hooks and stores two screens have to agree on — and a shared component that plays a cue or resolves a model needs the `audio` / `assets` barrels exactly as a screen does. `screens/` keeps only what the `GameScreenRegistry` names. On the three React surfaces the allowance is on the EXTENSION as well as the directory — a plain-`.ts` helper in `screens/`, `components/` or `shell/` is not a surface, while the composition root takes `.ts` because `register.ts` / `loaders.ts` are what it is; a game i18n token catalogue (`apps/<name>/{screens,shell}/translations/*.ts`) is narrower still — the i18n barrel and nothing else. The one non-barrel allowance is `@chimera-engine/renderer/shell/*`: the engine GUI routes an app's **own** Next host tree (`apps/<name>/renderer/app/**`) re-exports so both copies resolve through one package dist, **and** the shell composition modules such a route may compose rather than re-export (`shell/gameAssetSession`, which is how a game-owned page opens an asset session with no `GameShell` above it — Invariant #21). The allowance is on the importing FILE, not on the shape of the import: any file under `apps/<name>/renderer/app/**` may name any `shell/*` module, and it is forbidden from screens, shell contributions, and the composition root alike. (`styles/*.css` is a public **package** export for an app's global stylesheet, not a game-surface allowance: `no-game-renderer-internals` rejects it from every surface above.) The rule is on the **import specifier**, never on what the imported symbol is or where it happens to live: whatever a barrel re-exports is legal through that barrel — `components/ui` re-exports `EscapeStackProvider` and `useEscapeLayer` from `renderer/components/shell/`, and `components/r3f` re-exports `useTween` / `useCamera` / `useGameInteraction` from `renderer/hooks/` and the curve primitives from `renderer/utils/`, and a game surface may import all of them — while every other `@chimera-engine/renderer/*` specifier is a renderer internal, including stores, IPC bridges, `renderer/hooks/`, `renderer/utils/`, `components/shell/`, and an individual file behind a barrel — `renderer/assets/AssetManager.js` and every other file behind the `assets` barrel remain internal even though the barrel itself is public. `renderer/hooks/` and `renderer/utils/` are the reason the sentence reads this way rather than the other: each appears on both lists at once, public by what `components/r3f` names and internal by specifier, and there is no contradiction because the rule was never about where a symbol lives — `@chimera-engine/renderer/hooks/useCamera.js` stays a violation on the same day `useCamera` becomes public. Non-renderer game modules must not import renderer code at all. Each barrel is a curated re-export surface, not a directory opening: `assets/AssetManager.js`, `audio/AudioManager.js` and `input/InputManager.js` are violations exactly as `components/ui/Button.js` is (§3 mechanical check 17, ESLint `no-game-renderer-internals`).

**97.** Game-owned assets — audio, fonts, textures, models, and similar binary resources — must be committed and declared by the game package, not by `renderer/public`. Runtime renderer loading must resolve local `game-id/relative/path` references through the game-asset protocol. `GameFontFace.src` must not be an external URL, and runtime font loading must not fetch Google Fonts CSS or `fonts.gstatic.com` files; development-time downloads are allowed only through tooling that commits the resulting `.woff2` files into the game asset directory.

**98.** A _perspective_ replay (`PerspectiveReplayFile`, `kind: 'perspective'`) is the privacy-preserving counterpart to the deterministic `ReplayFile` of Invariant #71: it carries only already-projected `PlayerSnapshot` frames for a single, **locked, immutable** `viewerId` — never `seed`, `gameConfig`, or `actions` — so it exposes only what one player legitimately saw. A perspective replay is malformed (rejected at parse) if `viewerId` or `frames` is missing, if any `frame.snapshot.viewerId` differs from the file's locked `viewerId`, if any `frame.tick` disagrees with its embedded `frame.snapshot.tick`, or if frame ticks are not strictly increasing (playback walks `frames` in order, so duplicate or out-of-order ticks are rejected). The `kind` discriminator distinguishes it from the deterministic `ReplayFile` (which has no `kind`); both kinds coexist on disk (§4.28, ADR F44b).

**99.** Lobby match settings are **host-authored**; per-player attributes are **owner-authored**. `LobbyManager.setMatchSetting()` rejects (returns a rejected `Promise`) when the active session is not a hosted session — the host is the sole author of match settings, written through the host-only IPC channel `chimera:lobby:set-match-setting`. `LobbyManager.setPlayerAttribute()` instead enforces seat ownership: it rejects any `playerId` other than the caller's own ({@link LobbyManager.localPlayerId}); a hosted session merges the value into its own seat, while a joined (non-host) session forwards the own-seat intent to the authoritative host over the transport (`PLAYER_ATTRIBUTE_UPDATE`), and the host applies it to the **sender's** seat — derived from the connection, never a client-supplied id — via `HostTransport.onPlayerAttributeUpdate`. Both IPC channels are Zod-validated in `ipc-schemas.ts` and are the **sole** renderer write path. The merged `LobbyState.matchSettings` and `LobbyPlayerEntry.attributes` are broadcast to every peer on each change, so a joined client can author only its **own** seat's attributes (e.g. unit colour) and otherwise only reads the host's configuration — mirroring the owner-authored `ready` flow and extending the state-ownership rule of Invariant #36 to the lobby's pre-match config (§4.14, §4.37, F53).

**100.** Game `LobbyScreen` components (`apps/<name>/shell/*LobbyScreen.tsx`) perform **no privileged writes directly**. They receive `setMatchSetting`/`setPlayerAttribute` as `GameLobbyScreenProps` (`simulation/foundation/game-lobby-contract.ts`) and call those engine-provided setters, which route through the renderer lobby API (`useLobbyApi()`) and main-process IPC to `LobbyManager`. A game lobby screen must not write the IPC-mirrored `lobbyStore`, call `LobbyManager`, or open IPC channels itself, and it is reachable only as the registry-loaded `GameScreenRegistry.LobbyScreen` slot — mirroring the registry-indirection rule of Invariant #80 (§4.37, F53).

**101.** `GameSnapshot.setup` / `PlayerSnapshot.setup` (the agreed `GameSetupConfig` = match settings + per-player attributes) is **public host configuration** and is passed through `StateProjector.project()` **verbatim**: it carries no owner-only or per-viewer fields, so every viewer's projected snapshot exposes an identical `setup`. It is built from the agreed `LobbyState` (host-authored match settings + owner-authored per-player attributes) by `buildSetupFromLobbyState()` and carried into simulation via the `engine:start_game` action, keeping all peers in agreement — consistent with Invariant #36 (simulation-affecting parameters travel as match config, never as user settings) and Invariant #99 (§4.6, §4.14, §4.37, F53). The same verbatim-projection rule covers `GameSnapshot.matchId` / `PlayerSnapshot.matchId` (F68, #820): the host mints the stable match identity once per match start (`crypto.randomUUID()` in `onGameStartRequested`), carries it in the `engine:start_game` payload so deterministic replay reproduces it (Invariant #71), and `StateProjector.project()` passes it through verbatim — every viewer sees an identical `matchId`, `engine:return_to_lobby` preserves it, and the next `engine:start_game` mints a fresh one. The `SaveFile.session` manifest that records it alongside the seat roster is host-local orchestration metadata (Invariant #59 — raw ids and control kinds only, no profile data) and never appears in any projection or IPC payload (Invariant #108).

**102.** `GameReduceContext.endTurnGuard?` is the per-game end-turn gate, populated by `ActionPipeline` once from the active game's `GameDefinition.canEndTurn` hook (resolved via `ActionRegistry.resolveGame(gameId)`). It is consulted **only** by `engine:end_turn.validate()`, **after** the generic active-player checks, so a game can reject a premature end-turn (e.g. a commit-then-sync turn mode rejecting with `awaiting_commitment` until every seated player has committed for the current turn; §4.6/§8, F54) **without** the engine knowing any specific game. It satisfies the `GameReduceContext` JSDoc contract that adding a field to that ISP-narrow surface requires a dedicated invariant, mirroring #89 (`dispatchDepth`) and #90 (`logger`). Its sibling `GameReduceContext.endTurnAuthority?` — populated the same way, once, from the active game's `GameDefinition.mayEndTurn` hook — instead **replaces** the generic active-player check in `engine:end_turn.validate()` when present (absent ⇒ the default `playerId === turnClock.activePlayerId` stands), so a simultaneous turn mode can authorise **any** seated player to fire the reveal-only End Turn once every seat has committed (a commit-then-sync turn mode; §4.6/§8, F54), without the engine knowing any specific game. Game reducers must not read or repurpose `endTurnGuard` or `endTurnAuthority`; any future engine-reserved consumer must update this invariant (§4.7, F54).

**103.** A game opts into a **commit-then-sync** (simultaneous) turn mode via a synced, host-authored match setting that is **off by default** and carried in `snapshot.setup` (Invariant #101); the default sequential turn flow stays unchanged for that game and every other game. The host drives the whole commit→reveal→apply loop **solely** through the game-supplied `CommitmentTurnOrchestration` hooks (`stageOnCommit`, `shouldReveal`, `shouldAutoEndTurn`, `resolveRevealOrder`, `revealedActionsFor`) and never branches on a specific game id (reaffirms Invariant #2). In this mode `End Turn` is **reveal-only** — authorised through `GameReduceContext.endTurnGuard` / `endTurnAuthority` (Invariant #102) and enabled only once **every** seated participant (human and AI) has staged a commitment for the current turn (§4.6, §8, F54).

**105.** Game-defined per-turn resource state (action budgets and similar) lives in `GameSnapshot`, is **seeded, refreshed, and decremented solely by the game's own reducers** (deterministic — Invariant #2), and reaches clients only through `StateProjector.project()` (Invariant #8). **106.** The `ai/` package is the **game-agnostic AI framework only** — its sole top-level members are `engine/` (the reusable state-machine / command / scheduler primitives), `__tests__/`, `index.ts`, and `CLAUDE.md`. **107.** The game-agnostic packages `ai/` and `simulation/` must not **define** game-specific gameplay tokens — per-game constants (`<GAME>_*`, e.g. `TACTICS_*`) or per-game action-string namespaces (`'<gameId>:*'`, e.g. `'tactics:move_unit'`). **110.** The simulation is **language-agnostic**: game logic emits **stable identifiers, never user-facing strings**, and the i18n **runtime** (translation resolution, the ICU message formatter, the React binding — everything under `renderer/i18n/`) is a **renderer-only** concern that `simulation/`, `ai/`, and `networking/` must never import. **112.** Token resolution follows a fixed fallback chain — **`game override → engine English default → raw key`** (`resolveTranslation`). **114.** A **spectator** is a read-only session viewer, never a participant: it is never added to `GameSnapshot.players`, the host's seat ledger (`registeredPlayers` / `activePlayers` / the slot ledger), saves (`SaveFile.session`, Invariant #108), or replays; it receives no `HumanPlayerAgent`, never advances the match-start gate, and any `EngineAction` on its connection is dropped (spoofed-envelope protection). Admission is opt-in and gated twice at the host's join classifier (`classifyJoin`, `electron/main/lobby/joinClassifier.ts`, injected at the composition root where the host knows the manifest and live snapshot so `LobbyManager`/providers stay provider-agnostic — Invariant #38): a fresh join into a **running** match becomes a spectator **only** when the game declares the capability via `resolveSpectatorSupport(manifest)` (`GameManifest.spectators.mode: 'perspective'`) **and** the host enabled the reserved, `engine.`-namespaced, host-authored match setting `engine.allowSpectators` (`readAllowSpectators`, off by default, synced verbatim in `snapshot.setup` — Invariants #99 / #101); otherwise the join is cleanly rejected (`spectators_disabled` when the capability is present but the toggle is off, `match_in_progress` when the game declares no capability). Lobby-phase and reconnect joins are always players, unchanged. An admitted spectator is bounded per session (`DEFAULT_MAX_SPECTATORS`, shared by both providers — Invariant #41), follows exactly one seated player tracked in the host-local `SpectatorRegistry` (`spectatorId → followedSeatId`, pure orchestration state that likewise never enters the snapshot, saves, or replays), and is delivered that seat's already-projected `PlayerSnapshot` through the single `StateProjector.project()` gate (Invariant #8) — the same perspective projection as any seated viewer (Invariant #98), never `GameSnapshot` (Invariant #3). The renderer treats a spectator as read-only: `GameShell` locks controls and withholds the host-only save, `renderer/app/game/page.tsx` derives `isHost = false` for a spectator (a spectator following the host's seat has `viewerId === hostId`, so the role must override the id match — keeping the deterministic-replay export host-only, Invariants #71 / #98) and no-ops `sendAction` (§4.14, §4.6, F72).

**115.** The spectate-target switch is an **out-of-band, cosmetic** channel, never simulation — the direct analog of the CHAT / PROFILE_UPDATE out-of-band rule (Invariants #72 / #62). `SPECTATE_TARGET_UPDATE` is **never** an `EngineAction`, never advances `tick`, and never enters `ActionHistory`, saves, or replays. A spectator requests a new followed seat through `window.__chimera.spectate.setFollowedTarget` → `chimera:spectate:set-target` → `LobbyManager.setSpectatorTarget` → transport `sendSpectateTarget` → host `onSpectateTargetUpdate`; the host derives the spectator from the **connection**, never a client-supplied id (Invariant #99), validates the target is a currently-seated player, re-points the `SpectatorRegistry` entry (Invariant #114), and unicasts the newly-followed seat's projection (`broadcastSpectator`) so the switch is immediate. The switch changes only which already-projected perspective the viewer receives — it mutates no simulation state and is invisible to every other peer (§4.14, §4.6, F72).

**116.** Every fade, crossfade, fade-in, and cue operation writes **exclusively** to a voice's own stage-1 `GainNode`; the per-bus and master `GainNode`s are never written by these operations, so the three gain stages (`voiceGain → busGain → masterGain`) compose purely multiplicatively — a bus `duck` during a crossfade attenuates both tracks together, and a settings change mid-fade survives. Held by test, not by a linter — the target node is a runtime value the linter cannot tell apart: `AudioManager.test.ts` snapshots the bus and master `AudioParam` automation around every fade op and asserts neither is written, and does so by SNAPSHOT rather than by ramp count, since an op that wrote and then cancelled would leave the count unchanged (§4.25).

**117.** Cue validation is two-tier, discriminated by **provenance**: a _static_ synchronous reject at `play()` (already-invalid handle, **no** voice reserved) fires only when both bounds resolve to finite seconds synchronously — a raw number, `'start'`, or a `{ name }` present in the parsed sheet — **and** the order is already invalid (`to ≤ from`, `loopEnd ≤ loopStart`); otherwise a _dynamic_ resolve-clamp-`[0, duration]`-then-drop-window at `startVoice` applies (any `'end'`-relative or clamp-dependent bound). A `loopRegion` implies `loop = true`. For a looping voice `to` bounds **total elapsed play duration** (`resolve(to) − anchorSeconds`, measured from the clamped but **pre-fold** `from` and realized by `source.stop(startedAtContextTime + …)`), never a buffer-wrap position; `startOffsetSeconds` is the distinct **post-fold** entry offset passed to `start()` and used for fade timing, and measuring the window from it instead would overrun the authored bound (§4.25).

**118.** Cue/second resolution is **fail-soft** and never throws into a caller. A load-bearing unresolvable `{ name }` (e.g. `from` on a non-loop voice, name absent) or a `from` beyond `buffer.duration` abandons that play/fade as an invalid handle with one warning; a raw second and any end-point cue (`to`, `loopEnd`) clamp; a window collapsed only **after** clamping is dropped and playback continues; `parseAudioCueSheet` returns `null` for absent/malformed metadata (§4.25).

**119.** Fade-out-then-stop is realized **only** by scheduling `source.stop(rampEnd)` so the existing native `source.onended` handler drives the sole `releaseVoice` path — **no wall-clock timer schedules a release.** A voice stays in the pool with `handle.valid === true` for the whole ramp (phase `'fading-out'`, `scheduledStopAt` set, still re-targetable) and is invalidated exactly once, guarded by `voices.delete(id)` returning true (§4.25).

**120.** Any operation starting a new stage-1 ramp first cancels prior automation and re-anchors at the held value (`cancelAndHoldAtTime(now)` in try/catch, else `cancelScheduledValues(now)` + `setValueAtTime(held, now)` — the pattern `AudioBus.duck` already uses). `held` is `param.value` **only when the caller cannot do better**: that getter reports the value at the start of the current render quantum, so it cannot see automation written in this same turn and an unrendered `GainNode` reports its `defaultValue` of 1. A caller that just wrote the departure passes it (the fade-in's curve floor at `t0`); a caller that can merely bound it passes the bound (a live-voice fade caps the read at the voice's ceiling, since a stale read names a gain the voice cannot be at). That bound must only ever OVER-estimate, so it is recorded per RAMP and not per verb: a voice's settled ceiling says where its gain ends up, and **any** ramp in flight — a `fadeTo` travelling to an absolute target it installed at ramp start, or a `fadeOut` descending to `0` from wherever it was — leaves the voice off that value for the ramp's whole window. The bound there is the higher of the ramp's two endpoints (every curve is monotonic between them), expiring against `AudioContext.currentTime` rather than a timer, and recorded by the single helper every voice ramp goes through so it cannot fall behind a verb whose author forgot it. Capping against the settled ceiling instead would step the next fade DOWN to a gain the voice has not reached — the same artifact this rule exists to prevent, and on a cap that reads `0` it also silently degrades an exponential ramp to linear via its zero-departure branch. A bound cannot repair a read that is too LOW, so the one write that produces one is not bounded but RECORDED: an instant application lands its target with no ramp, moving the gain arbitrarily far in zero time, and the value it lands is exact until the next automation — the same helper stores it and later departures take it outright rather than reading a param that cannot see that write. Without it a single same-quantum read would freeze into the bound and outrank every truthful read for the whole of the following ramp. Both are corrective, not decorative — the fallback path writes `held` as an explicit anchor and `equalPower` derives every waypoint from it, so a misread inverts a fade rather than softening it. Exponential ramps clamp **both** departure and target off zero to a `1e-4` epsilon (terminal `setValueAtTime(0)` only when the requested target is 0; fall back to linear when the **departure** is legitimately 0, which no exponential ramp can leave). `equalPower` is a piecewise-linear `linearRampToValueAtTime` waypoint curve whose waypoints **depart from** the re-anchored held value — the re-anchor is what establishes that departure, so the waypoints themselves sample the curve strictly after the start time and the last lands exactly on the target — never `setValueCurveAtTime`, which does not compose with cancellation. No curve may hard-fail on a platform: `exponential` is feature-detected and degrades to linear when `exponentialRampToValueAtTime` is absent **or throws**, while `equalPower` is composed from `linearRampToValueAtTime` and so has nothing to detect (§4.25).

**121.** Any fade-in/out/to or crossfade linkage requested before a voice's source has started is stored on the `VoiceRecord` and applied atomically in `startVoice` at the real start time `t0`, in the fixed order `releaseOnStart` (never creates a source) → `pendingFadeIn` → `pendingFadeTo` → `linkedFadeOut`. No ramp is ever scheduled against a null source (§4.25).

**122.** Fade-to-cue and fade-to-end timing is computed from `startedAtContextTime`, `startOffsetSeconds`, the **decoded** buffer duration and the **effective** loop window — the window as actually started, since a region that collapsed after clamping may disable looping (it does when the region was the whole intent) and the requested intent would then name a period the voice never runs — against `AudioContext.currentTime` (dividing by the fixed `playbackRate === 1`), never wall-clock/`setTimeout`, so a fade completes at the intended sample position regardless of main-thread jitter (§4.25).

**123.** Voice preemption ranks voices for reclamation, **worst standing first**, on four lexicographic terms: `'fading-out'` voices first (cheapest to reclaim — a partition the remaining terms still rank inside), then **lower priority**, then — **among voices of equal priority** — a looping voice before a non-looping one (a loop runs until something else ends it, while an equally-important one-shot ends itself and cannot be re-triggered; a `to`-bounded loop schedules its own end but still counts as looping, since the term reads the loop window), then older sequence. Equivalently, **among voices on the same side of the `'fading-out'` split** (which outranks both terms): a looping voice is reclaimed before any equal-or-higher-priority non-looping voice, while a lower-priority non-looping voice still goes first. The loop term sits **below** priority deliberately — above it, no priority a game could name would lift a music bed clear of a one-shot. The loop test reads the **effective** loop window (`loopWindowSeconds`), falling back to the requested intent only while `'loading'` (as #122). The first term is the **phase**, not "is this voice doomed": a voice carrying `releaseOnStart` is condemned too, and cheaper still, but ranks as an ordinary voice. Being lexicographic over four per-record keys it is a strict total order, which the single-pass min-scan over an insertion-ordered `Map` requires — leave any pair incomparable and the scan promotes age to the deciding term. **No voice class is hard-exempt** — the scan is unfiltered — so a saturated 32-voice pool never deadlocks a higher-priority request; music continuity is achieved solely via a high recommended `MUSIC_PRIORITY` constant (`100`), never applied implicitly by bus or loop flag. A long music crossfade's dying tail may be reclaimed by an SFX burst — the _incoming_ track's continuity is preserved, only the already-dying tail is cut (§4.25).

**124.** Authored cue sheets exist only as `AudioClipMetadata` inside an `'audio-clip'` `AssetManifestEntry.metadata` and are structurally **opaque to `simulation/`/`ai/`** (extends Invariant #20): the simulation contract types `metadata` as `unknown`, `AudioCueName`/`AudioClipMetadata` are **defined sim-side** (`simulation/foundation/audio-cue-sheet.ts`) and consumed by the renderer — never the reverse — and the only reader/resolver is `renderer/audio` (import-banned from sim). The `audioClipEntry` builder only _writes_ the value; `AudioClipAsset`'s decoded shape is unchanged; cue names resolve only against the referenced clip's own sheet (no cross-clip lookup). Backed by the sim→renderer import ban and a type-key anti-rot test (§4.25, extends #20).

**125.** `validate-assets` validates every `'audio-clip'` cue sheet as a build-blocking check: each cue second is finite, `≥ 0`, and `≤ durationSeconds`; `defaultLoopRegion` names both exist in `cues` with `end > start`; a sheet that declares `cues` or `defaultLoopRegion` **without** `durationSeconds` fails (so every named cue is range-checked at build time, not just soft-clamped at runtime); malformed sheets fail CI. Readability is **one rule applied at three levels** — the manifest entry, the sheet, and its `cues` — each of which must be an inline object literal whose every member is a plain `name: value` pair under a literal key; anything else fails. Only a **readable, non-audio `kind`** exempts an entry, because an unreadable one cannot rule a cue sheet out, and a guard that accepted it would let a hidden `kind` and a hidden `metadata` compose into a pass. Sheets are therefore authored inline, on an entry written as an object literal or through `audioClipEntry`. The check does not reach exactly one thing: an `entries` element the walker cannot unwrap to an object literal at all — extracted to a constant, or built by a helper the walker does not peel (`manifestEntryBuilderKinds` in `electron/dev-tools/validate-assets/index.ts` is the peeled set) — which is skipped, the blind spot the walker has always had for `ref` and `kind` (§4.25, extends #22).

**126.** The public `AudioHandle` gains no fields; all start-time / offset / phase / schedule context lives on the internal `VoiceRecord`. The trust-boundary handle type is never spread-built (§4.25).

**127.** A game surface never mounts a raw `@react-three/fiber` `<Canvas>`: `GameCanvas` (`role="main" | "overlay"`, §4.22) is the **only** canvas root a game mounts — on every Invariant #96 surface (`apps/<name>/screens/`, `apps/<name>/components/`, `apps/<name>/shell/`, `apps/<name>/renderer/`) and equally on any other file in a game app; the enforcement arms scan the whole `apps/<name>/` tree. The canvas root is the seam where engine-wide display settings apply (the `display.targetFps` cap today), and the undetectable `frameloop="never"`-with-no-driver black canvas exists only when a game owns the root. Deliberately **name-based** where #96 is specifier-based, and the two shapes cannot be read as contradictory: #96 bans whole **specifiers** because nothing behind a renderer internal is legal for a game, while this invariant bans one **binding** (`Canvas`) whose legitimate siblings — `useFrame`, `useThree`, `type ThreeEvent` — share the `@react-three/fiber` specifier, so a specifier ban would flag every in-Canvas component. Two enforcement arms: ESLint `chimera/no-raw-r3f-canvas` (the precise arm — named, aliased, string-named, and re-export forms plus the namespace-shaped reaches `fiber.Canvas`, `fiber['Canvas']`, JSX `<fiber.Canvas>`, and `const { Canvas } = fiber`) and mechanical Check 32 (the belt-and-braces arm — a statement-joining import scan over `apps/*/`, word-boundary so `GameCanvas` never matches while `Canvas as X` does, with an every-run negative control). The split is recorded here once: namespace **member access** is invisible to Check 32 (nothing on the import statement names `Canvas`) and caught by the ESLint arm; dynamic `import()` destructuring and `require()` carry no statically named binding and are visible to **neither** arm. Type-only imports pass both arms — a type cannot mount a canvas. Renderer-**internal** code and tests keep using raw or fake `<Canvas>`: this invariant scopes game surfaces only (§4.22, §4.16).

**128.** `ReduceContext.beatReducer?` is the per-game per-beat reducer, populated by `ActionPipeline` once from the active game's `GameDefinition.onBeat` hook (resolved via `ActionRegistry.resolveGame(gameId)`, the same shape as #102's `endTurnGuard`). It is **engine-internal** — absent from the public `GameReduceContext` surface (ISP) and reachable only after a deliberate `isReduceContext()` narrowing call, as #90 states of `logger`. It is called by **`engine:tick` only**, exactly **once** per outer tick, **last** in the beat pass — after `TimerManager.advance`, after the `tick + 1`, after the timer-fired child dispatches, after the time-scale countdown and after the animation-window sweep — so the hook sees the post-sweep state and receives that sweep's closures as its third argument. The context it is handed is rebuilt **without** `dispatch`, `logger` or `beatReducer`, so `isReduceContext()` refuses to narrow it and a game's `onBeat` cannot reach `dispatch` (Invariant #89): a beat that must change state returns a new snapshot. The hook is **pure** and adds **no** nested dispatch, which is what keeps a match using it replayable under `ReplayPlayer`'s "+1 tick per recorded action" check (Invariants #70/#71) with no replay-side change. `#isClockOnlyTick` compares snapshots field by field, so what the hook's return costs on the wire is decided by the FIELDS it writes, not by whether it allocated a new snapshot: a fresh **shallow copy** is still clock-only, while a changed field or an added key is a full broadcast. Game reducers must not read or repurpose this field; any future engine-reserved consumer must update this invariant (§4.7, §4.20).

**129.** Beat-owned gameplay windows live on `BaseGameSnapshot.animationWindows` and are **host-only**: `StateProjector.project()` carries an explicit field allowlist that omits the registry, so no window record — id, owner, remaining beats or payload — ever crosses to a client or into a projected perspective (Invariants #1/#3). Records are INTEGER or `FixedPoint` throughout (Invariants #44/#75): the registry is serialised into saves and replayed, so a float would let two machines disagree, and every renderer-side quantity — seconds, phase, playback rate — belongs to the clip rather than here. `AnimationWindowManager` is the writer during a match, and its three verbs (`open`, `interrupt`, `advance`) are **pure**: none installs a `GameTimer`, dispatches an `EngineAction` or reads a clock (Invariants #2/#42/#43), so the same recorded action reproduces the same registry. Within a match a window leaves through one of the manager's **four** paths, each reported on the same `ClosedAnimationWindow` shape with a distinguishing `reason` — `'expired'` (the countdown reached zero), `'owner-gone'` (the owning entity is no longer live, checked FIRST so it stays the truthful reason on the beat the countdown would also have run out), `'replaced'` (a second `open` under the same id, the `TimerManager.create` idiom, which reports the displaced instance rather than losing its close event), and `'interrupted'` (an ordinary game reducer closing it early — a stagger, a cancel, a death). The **match boundary** is not one of them and is stated here rather than left to be discovered: `animationWindows` is a `MatchScopedSnapshotKey`, so `engine:start_game` and `engine:return_to_lobby` rebuild the snapshot through `baseSnapshotOnly` and the whole registry goes with no per-window event at all — the same reset that drops a game's own extension fields, in the same reduce, which is why no listener survives to have wanted one (§4.7, §4.20).

**130.** The renderer turns `PlayerSnapshot.timeScalePermille` into a playback multiplier in exactly **one** place: `renderer/animation/timeScaleStore.ts`'s `setAuthoritativePermille`, which calls `timeScaleMultiplier` from `@chimera-engine/simulation/foundation/time-scale.js` and performs no arithmetic of its own — pinned by a source scan asserting that the module's comment- and string-stripped residue carries no division and no literal `1000`, with a positive control showing what a hand-rolled division would leave. That helper and `dilatedBeatPeriodMs` divide by the same `clampTimeScalePermille` result, so the host's beat period and the renderer's clip rate stay reciprocal by construction and the `[50, 4000]` clamp plus the fractional-permille refusal have a single definition. `useClipPlayer` follows that store unless `options.timeScale` names a multiplier, which OVERRIDES rather than composes: an authoritative dilation therefore reaches every mounted clip with no per-call-site wiring, and `useAnimationTimeScale` (the `components/r3f` barrel's read seam, Invariant #96) is how everything a game animates by hand opts in. The multiplier scales clip playback **only** — never the R3F clock, which `PerfProbe` reads and which F80 repaired, so a dilated match must report the undilated frame rate (§4.16, §4.22).

**131.** `renderer/components/shell/TimeScaleBridge.tsx` is the **sole** writer of that store, and it carries one integer in one direction: it takes `snapshot.timeScalePermille` as a **prop** from `GameShell`, which already holds the snapshot, and no animation state, clip position, marker or mixer value is ever written back. It is mounted **once**, inside the single element expression both of `RegistryGameShell`'s return paths return, so a game declaring no `eventAudioBinding` (the blank scaffold included) mounts it exactly as one that does; a mount site inside the audio fragment would leave dilation dead for that game while the host ticker still re-paced the match. Its unmount seats real time again: the multiplier belongs to a live snapshot, and a leftover one would slow every clip the app mounts afterwards with no writer reachable to reset it (`setState` is withheld per §5.5 and the writer reaches no barrel).

**132.** No animation event may gate an `EngineAction`. A clip's marks — `notify`, `passage-start`, `passage-tick`, `passage-end`, `clip-end` — are renderer-local reports of where a playhead is, and a gameplay consequence derived from one would be derived from the FRAME CLOCK, which no two machines share (Invariants #42/#43, #56–#58). The rule is held by **absent parameters**, not by review: `ClipMarkerHandlers` and every event it carries name no dispatcher, no `SendAction`, no `PlayerId` and no `tick`, and neither `ClipPlayer` nor `useClipPlayer` adds one — all three modules are read by the census that pins this — so a handler has nothing to dispatch WITH, and the shape is the enforcement. The same absence runs the other way: no mixer, clone, playhead, marker or clip-speed value enters a `GameSnapshot`, a Zustand store, an IPC payload, a save or a replay. Where a beat-denominated consequence is wanted the simulation owns it — the passage's authored `beatWindow` (Invariant #129), reconciled against the clip's positions at content load and never derived from them at reduce time (`chimera/no-animation-derivation-in-reduce`). Stated as an invariant rather than left to be inferred from one hook's signature, because a future animation surface adding a handler parameter would be adding it to a shape no invariant had claimed (§4.16, §4.22).

**133.** A client-side asset preload never gates a MOUNT and never gates the host's scene barrier. `useCriticalAssetPreloadGate` withholds only the app-level `fadeIn` on a route that reveals a game scene, and `startScenePreload` withholds only the `engine:scene_ready` dispatch inside the two-phase transition; both settle on **four independent paths** — success, rejection, an elapsed budget (`CRITICAL_ASSET_PRELOAD_BUDGET_MS` = 8 s, `SCENE_PRELOAD_BUDGET_MS` = 5 s, deliberately below the barrier's observable e2e deadline), and a nothing-to-load short-circuit — so no combination of a missing, slow or undeclared asset can produce a permanently black screen. A THIRD asset wait sits ahead of both and is bounded on the same terms: `loadRendererGame`/`loadRendererGameShell` await a loaded shell's fonts, preload images and cursor textures before resolving, and `GAME_SHELL_WARMUP_BUDGET_MS` (5 s) releases that warm-up while reporting the steps it left undone. Each of those has a degraded form the shell can render — a decode the first paint would have done anyway, an unwritten cursor token leaving the engine's stock cursor — so it fails open like the other two. What stays unbounded is the `RendererGameLoader` call ABOVE that warm-up, the game's own dynamic `import()`: an absent `GameScreenRegistry` has no degraded form, so the only settle a budget could add there is a throw, which turns a slow module into a refused route. Its ceiling is the bundler's rather than the engine's, and what that ceiling does and does not cover is recorded in `docs/core-components/asset-reference-system.md` — the guarantee above is over ASSETS, and a module chunk is not one. `GameShell` mounts on the same commit it does today, which is what keeps the unique disposer of a page-injected `AssetManager` reachable (Invariant #21); `/replays/player`'s `isReady` is never widened for the same reason, and its cover is an overlay above a mounted shell. `engine:scene_ready` carries `{ playerId }` and nothing else, so no client's load timing, fraction or outcome ever enters authoritative state — decisive because the host barrier waits for every player and evaluates `timeoutTicks` only when an action is applied, so a withheld ack in a turn-based match freezes the tick and the host timeout can never fire. A seat in `state.players` with no mounted `SceneRouter` — a disconnect mid-transition, or an AI seat — produces no `engine:scene_ready` at all, and `SceneTransitionState.timeoutTicks` cannot cover for it because a tick advances only when an action is applied. That seat is released by a FOURTH budget, the host's: `SessionRuntime` measures a pending transition against `DEFAULT_SCENE_TRANSITION_BUDGET_MS` (30 s, above every client budget above it so a slow-but-live client is never mistaken for one that cannot ack) and dispatches `engine:scene_expire`, which sets `SceneTransitionState.expired` and lets the descriptor's own `onClientTimeout` choose commit or drop exactly as the tick budget does. The wall clock stays in the host runtime, never in a reduce (Invariants #2 / #42 / #43), and the expiry carries no payload. The loading beat (§4.36) is an unconditional BEAT on a RESOLVED cover rather than a release budget: on a ROUTE ENTRY that reveals a game scene — `/game` and `/replays/player` — wherever the cascade resolves a game-declared cover form, the local reveal passes through a fixed sequence — black, that cover for at least `max(gate settle, resolveLoadingBeatFloorMs)`, black, the reveal — and what it defers is the local reveal and the chrome's mount, never a mount of `GameShell` itself, an ack, or the host barrier. Those are two terms, not one: the layout-bearing HUD row mounts at the COVERED leg, because it is a grid row whose arrival re-fits the canvas below it over two observer round-trips, and a re-fit begun at the reveal lands inside the fade; only the Escape-bearing in-game menu waits for the reveal itself. The scene-to-scene cover site inside `SceneRouter` runs that same sequencer, so the statement above is a universal over every reveal that passes through a curtain rather than a route-only rule. It sequences with `ownsDarkening: false` and `ownsReveal: false`: `useFadeTransition` commands the fade-out, because the ack awaits it, and performs the reveal, because it is the hook the transition earned it from — the beat still enters `revealing` on the same terms, so only the `fadeIn` call sits elsewhere. A within-scene SCREEN SWITCH (`navigateToScreen`) is not a counter-example but a different wait: nothing fades for it, so it has no curtain owner and no beat, and its Suspense cover is floored by `useMinimumVisibleHold` alone. A `settled` term folds in a pending code-split chunk only where the surface's OWN cascade resolved a cover — the route entries resolve the key the route owns, the hop the entering scene's — which DEFERS a reveal across the `React.lazy` wait left unbounded above; what bounds the harm is the LAYER rather than a budget: the beat's cover stays mounted above the curtain, so a chunk that never resolves parks the player on the game's declared loading screen and never on black. What a hop additionally does with the Suspense site's own cover is Invariant #88's. Where the cascade resolves NO cover, nothing is folded in: the beat parks on `covered`, a phase that mounts no cover at all, so the deferral would hold the curtain over nothing — the reveal waits on the commit (a hop) or on the asset gate (a route entry) alone, and the chunk wait falls back to the Suspense fallback exactly as before. Arming on a resolved cover rather than on a visible one is what makes it reach a wait that settles before anything could have been shown; the previous shape could not, and on the hardware that reads a loading screen fastest it showed none. The sequence adds no release path of its own: every timer the beat arms only ever EXTENDS a wait — the floor and the fade legs. A wait that goes unsettled AGAIN inside the closing leg is a new wait, and the beat does not re-open the cover it is already closing for it. Its durations reach it from resolvers that return `0` under `NEXT_PUBLIC_CHIMERA_E2E`: `screenFadeMs()` for the fades on both surfaces — which also collapses under `prefers-reduced-motion`; the scene surface reads it as the default of a `fadeInMs` prop a page may pin — and `loadingCoverHold.ts` for the floor, which deliberately does NOT collapse under reduced motion, zeroed fades being exactly when an unfloored cover is sub-perceptual. The beat is a deliberate delay rather than a gate. The sequencer itself reads no environment, so the flag keeps the readers it already had. So the clause that follows keeps its full strength: no budget named here collapses under `NEXT_PUBLIC_CHIMERA_E2E` — the e2e build is where a never-releasing gate is observed, and a gate disabled there would make its own spec pass vacuously (§4.10, §4.18–§4.19, §4.33–§4.36).

**134.** Spatial attenuation is realised exclusively by a voice's own `PannerNode` and the single shared `AudioContext.listener` (§4.25): no spatial code path writes any of the three gain stages — extending #116, so a spatial voice ducks, follows its bus volume and fades exactly as a non-spatial one — and the engine **never derives the listener pose from a camera**. `setListener` takes a plain, game-supplied tuple pose (`AudioListenerPose`); there is exactly **one** listener per app, shared by every canvas, and an overlay canvas must not move it; the audio module graph imports neither `three` nor `@react-three/fiber`, so nothing camera-shaped can reach the pose. The panner sits **between** stage 1 and stage 2 of the voice chain, `panningModel` is pinned to `'equalpower'` and is not authorable — `SpatialOptions`' closed key set is type-pinned — and authored distances join the **static** validation tier by #117's provenance rule: an inverted band rejects synchronously at `play()` with an invalid handle and no voice reserved, and an equal pair is realised as the narrowest band the continuous model can express through a named constant. Moving a source (`setVoicePosition`) and moving the listener write only positional `AudioParam`s over a shared anti-zipper window, park on the `VoiceRecord` while a voice loads (#121's pending discipline), and never touch a gain stage. **Code-verified** rather than mechanically enforced: what this invariant asserts is which NODE a write lands on, which no grep or lint rule can observe — the roll-call row names the spy tests that hold it (§4.25).
